# 三点 MOOC 补齐与后台更新（2026-10-19）

三个此前为零的知识点现在各有 **1 门**通过自身大纲校验的 MOOC。当前预览库已导入 **4 门有效公开课程大纲**，其中 3 门分别满足这三个知识点；另 1 门仅作为公开目录保留，不会因入库就进入推荐。默认每点 3 门的数量目标仍未达到。

共享课程库只在后台工作，前端不增加课程库入口、命中标签或刷新配置。B站来源、轮数和封面界面保持原行为；搜索、校验、显示继续使用 SSE。

## 更新机制

- 本机启用 `MOOC_REFRESH_ENABLED=true`、`MOOC_REFRESH_INTERVAL_SECONDS=86400`。每个知识点按查询来源分别记录最近一次真实、成功且无来源警告的搜索时间。
- 下次搜索时，如果已有足够课程但超过 24 小时，仍用首轮的一个查询名额寻找更新；不增加既定查询槽数或额度上限。宽课程词与细知识点词轮换，新发现课程通过完整大纲校验后才流式加入结果。
- 24 小时内已满足数量目标则复用；不足默认 3 门仍按缺口补搜。没有无人访问时的后台定时抓取。
- 五分钟持久化租约抑制重复刷新，使用 SQLite 原子抢占。缓存命中、失败、部分来源失败都不能冒充一次成功更新；实际 403、429、robots 或验证码仍停止对应来源。
- 课程证据仍按原抓取时间默认 7 天失效，读取和搜索不能续期。到期后须重新取得课程自己的公开大纲。

实现：[刷新状态](../backend/app/mooc_refresh.py)、[查询调度](../backend/app/platform_search.py)、[课程库](../backend/app/course_library.py)。模板配置仍默认关闭刷新，由部署者显式启用。

初次扩大查询暴露了采集层与召回层入口规则不一致：召回已接受合法 `outVendor`、数字 `cid` 详情入口，旧采集规则仍在请求前阻止。现在两层使用同一个精确公开入口验证函数，原始 URL 不改写、每个别名独立取得证据，学习页、账号、播放、API 和任意参数仍不允许。MOOC 页缓存增加单独版本，B站页缓存不变。修复后的 SQL 补测保留此前隔离实验库，实际新发 1 次搜索和 3 次页面/robots HTTP，完整大纲通过后跳过剩余查询。没有借用另一个 URL 的大纲。

首次 B站返回 24 条不同链接（pandas 14、HTML 10、SQL 0）；9 次搜索中 6 次出现上游引擎失败，整体任务保留 `partial`。这不是 B站全平台可用性的承诺。

首次 Tavily 在约 91.9 秒出现 MOOC、SQL 补测在约 13.2 秒出现课程，均在任务结束前流式显示。Serper 阶段先从库显示两门课程，再继续补搜。暖库验证把目标设为每点 **1 门**，三个知识点全部复用成功，0 搜索、0 新详情请求，约 537 毫秒得到三门课；这一快速暖任务首次数据已是终态。计时来自生产 SSE 生成器的进程内观测，不是浏览器网络延迟。

SQL 补测脚本首次衔接三点暖任务时，仍保留单点两次预算，被正常准入检查拒绝；没有额外请求。之后单独恢复暖测，预留六个计划槽但实际 provider 请求硬上限为零，结果如上。初次失败、修复前结果与复测分别保留，没有覆盖旧记录。
